## 1. Phạm vi và công nghệ đã xác minh

- FR-01 tương ứng task `N2LHTBLTT-8`: đăng ký khách hàng.
- FR-02 tương ứng task `N2LHTBLTT-9`: đăng nhập, đăng xuất, kiểm tra phiên. Refresh là phần hỗ trợ vòng đời phiên; FR-09 trong bảng Jira hiện tại là hủy đơn.
- Dự án chung dùng ASP.NET Core / .NET 10, EF Core / Npgsql, PostgreSQL và BCrypt.Net-Next. Đây là bản tích hợp theo repository nhóm.
- Module Identity sở hữu `identity.users` và `identity.refresh_tokens`. Các migration đã có trên `toandev`; thay đổi này không bổ sung bảng/cột/migration.

Giữ JWT + refresh token của nhánh nền. Cơ chế phiên ở đây là **JWT tham chiếu trạng thái trong DB**, không phải cookie session thuần của Express hay ASP.NET Cookie Authentication.

## 2. API contract

| Method / route | Dữ liệu và điều kiện | Thành công | Lỗi chính |
|---|---|---|---|
| `POST /api/v1/auth/register` | JSON: `email`, `password`, `fullName`, `phone` tùy chọn | `201`, tự đăng nhập, JWT trong `data`, refresh cookie | `400` validation, `409 EMAIL_ALREADY_EXISTS` |
| `POST /api/v1/auth/login` | JSON: `email`, `password` | `200`, JWT và cookie phiên mới | `400`, `401 INVALID_CREDENTIALS`, `403 ACCOUNT_LOCKED` |
| `GET /api/v1/me` | `Authorization: Bearer <accessToken>` | `200`, hồ sơ của subject trong JWT | `401 UNAUTHORIZED` |
| `POST /api/v1/auth/refresh` | Cookie `phonestore_rt`, cookie `phonestore_csrf`, header `X-CSRF-TOKEN` khớp cookie CSRF | `200`, cặp token mới | `401 REFRESH_TOKEN_MISSING/INVALID`, `403 CSRF_TOKEN_INVALID` |
| `POST /api/v1/auth/logout` | Cookie refresh hoặc JWT còn hợp lệ; luôn cần cookie/header CSRF | `200`, thu hồi phiên và xóa refresh cookie | `403` khi CSRF/Origin không hợp lệ; `500` nếu lưu thu hồi thất bại |
| `GET /api/v1/auth/csrf` | Không cần đăng nhập | `200`, phát/ghi lại cookie CSRF | — |

Đăng ký/đăng nhập không cần CSRF header. Các request thay đổi trạng thái dưới `/api/v1/auth` có `Origin` phải cùng origin với API hoặc thuộc `Cors:AllowedOrigins`. Postman/cURL không gửi `Origin` vẫn được sử dụng; `Origin` không thay thế xác thực.

Quy tắc giữ theo validator của nhóm:

- Email hợp lệ, tối đa 254 ký tự; lưu và tra cứu sau khi trim, chuyển chữ thường.
- Mật khẩu đăng ký dài 8–72 ký tự, có chữ và số; không trim mật khẩu. Login giới hạn tối đa 72 ký tự.
- Họ tên không trắng, tối đa 100 ký tự. Điện thoại tùy chọn, theo regex sẵn có của Identity.
- Mật khẩu được băm bằng `BCryptPasswordHasher`; refresh token là 64 byte ngẫu nhiên, DB chỉ lưu SHA-256 của token.

Response đăng ký/đăng nhập/refresh sử dụng envelope có sẵn:

```json
{
  "success": true,
  "message": "...",
  "data": {
    "userId": 123,
    "email": "customer@example.com",
    "fullName": "Khách hàng",
    "role": "CUSTOMER",
    "accessToken": "<JWT>",
    "expiresAt": "<UTC>"
  },
  "timestamp": "<UTC>"
}
```

Các số và token trong ví dụ là minh họa. `refreshToken` không xuất hiện trong JSON. Lỗi sử dụng `ErrorResponse` của BuildingBlocks: `code`, `message`, `fieldErrors` khi có validation, `requestId`, `timestamp`.

## 3. Luồng thực thi và transaction

```mermaid
sequenceDiagram
    actor Client
    participant API as Host / JWT Bearer
    participant Controller as AuthController
    participant Service as IdentityService
    participant DB as PostgreSQL / identity
    Client->>API: POST /auth/register hoặc /auth/login
    API->>Controller: Origin hợp lệ, JSON hợp lệ
    Controller->>Service: Request đã qua FluentValidation
    Service->>DB: BEGIN; tạo user hoặc kiểm tra mật khẩu
    Service->>DB: Lưu hash refresh token
    Service->>DB: COMMIT
    Service-->>Controller: JWT có sid và refresh token gốc
    Controller-->>Client: JSON JWT + cookie refresh HttpOnly + cookie CSRF
    Client->>API: GET /me + Bearer JWT
    API->>API: Kiểm tra chữ ký, issuer, audience, thời hạn
    API->>DB: sid còn hiệu lực? User còn hoạt động, đúng role?
    API-->>Client: 200 hoặc 401
    Client->>Controller: POST /auth/logout + cookie/header CSRF
    Controller->>Service: Thu hồi hash của cookie hoặc sid đã xác thực
    Service->>DB: UPDATE phiên thành IsRevoked
    Controller-->>Client: 200 + xóa refresh cookie
    Client->>API: Dùng lại JWT cũ
    API->>DB: Kiểm tra sid
    API-->>Client: 401
```

`sid` là hash của refresh token tương ứng, không phải refresh token gốc. Có `sid` không cho phép tính ngược refresh token ngẫu nhiên.

- **Đăng ký:** user và phiên phải cùng commit; cấp/lưu token lỗi thì rollback user. Unique index email xử lý cạnh tranh; vi phạm đúng `IX_users_Email` được chuyển thành `409`.
- **Login:** khóa dòng user trong transaction trước khi kiểm tra mật khẩu/cấp phiên. Dùng cùng thứ tự khóa với các thao tác bảo mật tài khoản.
- **Refresh:** khóa user trước; `UPDATE ... WHERE !IsRevoked AND ExpiresAt > now` tiêu thụ token cũ; lưu token mới rồi commit. Hai request cùng token chỉ một request thành công. Lỗi tạo token mới rollback cả việc tiêu thụ token cũ.
- **Logout:** lặp lại với CSRF hợp lệ vẫn trả `200`. Không bắt JWT còn hạn vì người dùng có thể logout bằng refresh cookie. Không có cookie thì chỉ dùng `sid` từ JWT đã được xác thực, không nhận session ID từ body/header tùy ý.
- **Đổi/reset mật khẩu, đổi vai trò, khóa tài khoản:** cập nhật user và thu hồi các phiên cùng transaction; các JWT đang tham chiếu phiên đó bị từ chối ở request tiếp theo.

Cookie refresh: `HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` khi request HTTPS, thời hạn lấy từ `Authentication:RefreshTokenDays`. Cookie CSRF đọc được bởi JavaScript và giữ lại sau logout; nó không phải thông tin đăng nhập.

## 4. Những thay đổi client cần biết

1. JWT cũ chưa có `sid` bị từ chối. Sau tích hợp cần đăng nhập lại.
2. Refresh xoay **cả cặp token**: phải thay Bearer token bằng `data.accessToken` mới. Chỉ nên có một request refresh đang chạy cho mỗi phiên; request thua cuộc nhận `401`.
3. Logout xong, xóa JWT trong bộ nhớ client. Gửi lại JWT cũ sẽ nhận `401`; các thiết bị khác vẫn giữ phiên riêng.
4. Cookie refresh không tự xác thực các API như `/me` hay Cart/Order. Các API này cần Bearer JWT.
5. Request auth và `/me` trả `Cache-Control: no-store`.
6. Mặc định không mở CORS có credentials cho origin bên ngoài. Ví dụ frontend local cùng site:

   ```powershell
   $env:Cors__AllowedOrigins__0 = 'http://localhost:5173'
   ```

   Frontend dùng `credentials: 'include'`; đọc `phonestore_csrf` và gửi header `X-CSRF-TOKEN` khi refresh/logout. `SameSite=Strict` yêu cầu frontend/API cùng site; cấu hình CORS không tự thay đổi quy tắc SameSite. Dùng nhất quán `localhost` thay vì trộn với `127.0.0.1`.

## 5. Chạy và kiểm tra local

Chạy lệnh tại thư mục chứa `PhoneStore.slnx`. Cần .NET **10** SDK và PostgreSQL. Có thể dùng PostgreSQL sẵn có hoặc `docker compose -f docker/docker-compose.yml up -d` khi Docker đang chạy.

```powershell
dotnet restore PhoneStore.slnx
dotnet build PhoneStore.slnx --configuration Release
```

Nếu DB của task -7 đã áp dụng các migration của `toandev`, có thể chạy Host ngay. Nếu dùng DB mới, cần áp dụng migration **cả năm module trước khi chạy**: Host có seed Development nhưng không tự migrate DB. Dùng `dotnet-ef` cùng major 10 (nên khớp EF Design 10.0.13); không tạo migration mới cho FR này.

```powershell
$env:ASPNETCORE_ENVIRONMENT = 'Development'
# Đặt ConnectionStrings__DefaultConnection theo DB local của nhóm nếu khác mặc định.
$taskHost = 'src/Host/PhoneStore.Api/PhoneStore.Api.csproj'
$taskModules = @('Identity', 'Catalog', 'Cart', 'Order', 'Inventory')
foreach ($taskModule in $taskModules) {
    dotnet ef database update --context "${taskModule}DbContext" --project "src/Modules/$taskModule/PhoneStore.Modules.$taskModule" --startup-project $taskHost
    if ($LASTEXITCODE -ne 0) { throw "Migration $taskModule thất bại; kiểm tra lỗi trước khi tiếp tục." }
}
dotnet run --project $taskHost --launch-profile http
```

Swagger: `http://localhost:5122/`. Các lệnh EF trên là hướng dẫn cho DB local; kết quả kiểm thử tự động trong tài liệu validation sử dụng `DatabaseMigrator` có sẵn trong project test.

Kiểm tra tự động:

```powershell
# User kết nối này cần quyền tạo/xóa DB test. Điền connection string local, không commit secret.
$env:PHONESTORE_TEST_ADMIN_CONNECTION = '<connection string tới database postgres>'
dotnet test PhoneStore.slnx --configuration Release
# Chỉ các ca hồi quy mới của phiên:
dotnet test tests/PhoneStore.IntegrationTests/PhoneStore.IntegrationTests.csproj --filter 'FullyQualifiedName~IdentitySessionRegressionTests'
```

Fixture tự tạo và xóa `phonestore_test_<guid>`, áp dụng các migration trước khi seed. Không trỏ thao tác thử nghiệm trực tiếp vào DB có dữ liệu quan trọng.

## 6. Kịch bản nghiệm thu bằng Postman

Hướng dẫn từng thao tác và bảng 18 ca: [TEST-POSTMAN.md](TEST-POSTMAN.md). Collection có sẵn: [PhoneStore-FR01-FR02.postman_collection.json](../../postman/PhoneStore-FR01-FR02.postman_collection.json).

1. Register email mới, password hợp lệ, fullName → `201`, `role=CUSTOMER`, không có hash/refresh token trong JSON. Kiểm tra hai cookie trong Postman Cookie Manager.
2. Register lại email, kể cả đổi hoa/thường → `409`. Email sai/mật khẩu thiếu số → `400`.
3. Login sai mật khẩu hoặc email không tồn tại → cùng `401 INVALID_CREDENTIALS`. Login đúng → `200` và phiên mới.
4. Gắn `Authorization: Bearer <data.accessToken>`; `GET /api/v1/me` → `200`. Bỏ JWT, gửi JWT giả hoặc chỉ `X-User-Id` → `401`.
5. Lấy giá trị `phonestore_csrf` trong cookie; thêm header `X-CSRF-TOKEN` bằng đúng giá trị đó. POST refresh → `200`; thay JWT bằng token mới. JWT cũ → `401`; JWT mới → `200` trên `/me`.
6. POST logout có CSRF → `200`; dùng JWT vừa logout gọi `/me` → `401`. Refresh cookie đã thu hồi không làm mới được. Gửi lại logout với CSRF hợp lệ → `200`.
7. Xóa header CSRF rồi refresh/logout → `403`. Gửi `Origin: https://untrusted.example` vào register/login → `403`.
8. Đăng nhập cùng tài khoản trên hai cookie jar riêng; logout một jar, jar còn lại gọi `/me` vẫn `200`.

Các ca concurrent register/refresh, rollback khi lưu token lỗi và thu hồi mọi thiết bị có test tự động; Postman tuần tự không đủ chứng minh các trường hợp cạnh tranh.

## 8. Trade-off và giới hạn đã biết

- Mỗi request mang JWT cần truy vấn phiên trong DB để thu hồi có hiệu lực ở request tiếp theo. Đổi lại, API phụ thuộc DB và có thêm chi phí truy vấn. Chưa đo tải để kết luận độ trễ/công suất.
- Khóa dòng user làm các thao tác cấp/thu hồi phiên cùng tài khoản chờ nhau. Phù hợp phạm vi đồ án; chưa benchmark tải đồng thời lớn.
- Không hủy các request đã qua xác thực và đang chạy khi logout. Refresh tạo phiên mới; chưa có session family/reuse-detection thu hồi dây chuyền khi token cũ bị phát lại.
- Development sinh khóa ký ngẫu nhiên trong process nếu không cấu hình khóa. Restart làm JWT cũ hết hiệu lực; có thể refresh bằng cookie còn hạn hoặc login lại. Chạy nhiều instance cần dùng chung khóa được quản lý qua môi trường/secret store.
- Ngoài Development phải đặt `Authentication__SigningKey` đủ độ dài/ngẫu nhiên, `Authentication__AllowDevelopmentSigningKey=false`. Khóa ngắn được cấu hình sẽ bị báo lỗi, không âm thầm fallback.
- Chưa bổ sung rate limit/khóa đăng nhập theo số lần sai, MFA, xác minh email, dọn token hết hạn hay triển khai HTTPS/reverse proxy. Đây là việc cần đánh giá trước khi công khai dịch vụ; không thuộc bằng chứng nghiệm thu local hiện tại. Đặc biệt `Secure` phụ thuộc `Request.IsHttps`, nên cần cấu hình proxy/HTTPS đúng khi triển khai.
- Chưa push, mở PR, merge hoặc thay đổi trạng thái Jira. Khi tích hợp cần đối chiếu nhánh đích với trưởng nhóm vì `develop` hiện cũ hơn nền `toandev` đã chọn.
