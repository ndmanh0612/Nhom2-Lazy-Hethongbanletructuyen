3. Kiến trúc & mô hình dữ liệu

Thiết kế bám theo đúng convention của Identity và Catalog đã có sẵn: Domain entity dùng private set + static Create() factory, đặt quy tắc nghiệp vụ trong method domain (không để lọt sang service), EF mapping khai báo tường minh trong OnModelCreating.

┌─── MODULE CART ── schema: cart ─────────────────┐ │ Cart ──1:N──▶ CartItem ├─ Id (bigint, identity) ├─ UserId (bigint) ◀── FK logic tới Identity.users ├─ Status (varchar 20, enum→string) ├─ CreatedAt / UpdatedAt └─ Items (navigation, cascade delete) CartItem ├─ Id / CartId ├─ ProductVariantId (bigint) ◀── FK logic tới Catalog ├─ ProductName / Sku (snapshot) ├─ UnitPrice (snapshot lúc thêm) └─ Quantity │ └──────────────────────────────────────────────┘ ┌─── MODULE ORDER ── schema: ordering ───────────────┐ │ Order ──1:N──▶ OrderItem + OrderStatusHistory ├─ Id / OrderNumber (unique) ├─ CustomerId (bigint) ◀── FK logic tới Identity.users ├─ Status (enum→string) / PaymentMethod (COD) ├─ Subtotal / ShippingFee / TotalAmount ├─ ReceiverName / Phone / ShippingAddress └─ Items + StatusHistories (cascade delete) │ └──────────────────────────────────────────────┘
Nguyên tắc cô lập schema được giữ: CartDbContext và OrderDbContext dùng cùng một connection string nhưng HasDefaultSchema(...) tách bảng và MigrationsHistoryTable tách lịch sử migration theo từng schema. Không có FK vật lý giữa các schema — các liên kết UserId, ProductVariantId là FK logic, đúng theo ranh giới Modular Monolith của đề tài.

4. Review Cart module

4.1 Entity Cart — Aggregate Root

public class Cart : AggregateRoot<long>
{
    public const int MaxItemsPerCart = 50;

    public long UserId { get; private set; }
    public CartStatus Status { get; private set; } = CartStatus.ACTIVE;

    private readonly List<CartItem> _items = [];
    public IReadOnlyCollection<CartItem> Items => _items.AsReadOnly();

    public int TotalQuantity => _items.Sum(item => item.Quantity);
    public long Subtotal => _items.Sum(item => item.Subtotal);

✔ Điểm tốt

  • Quy tắc nghiệp vụ nằm đúng chỗ — AddItem tự cộng dồn khi trùng variant, tự chặn giỏ đã convert.
  • MaxItemsPerCart = 50 chặn giỏ phình to vô hạn.
  • EnsureItemBelongsToCart chặn việc thao tác nhầm lên item của giỏ khác.
  • Computed property Subtotal/TotalQuantity không lưu DB → không lệch dữ liệu.
  • Pattern static Create() + private set khớp với User/Product.

⚠ Cần chú ý

  • CartItem.Create(Id, …) — khi giỏ chưa lưu, Id = 0. Phụ thuộc EF fixup để gán FK (xem F-01).
  • MarkAsAbandoned() hiện chưa có nơi gọi — sẽ dùng cho job dọn giỏ bỏ quên (chưa có task).
  • Chưa có AddDomainEvent cho sự kiện giỏ — cần khi tích hợp tồn kho (task 26).

F-01 · Critical Client có thể tự khai giá sản phẩm — rủi ro thao túng đơn hàng

Contract AddToCartRequest nhận UnitPrice, ProductName và Sku trực tiếp từ request của client:

public record AddToCartRequest(
    [Required] long ProductVariantId,
    [Required, MaxLength(200)] string ProductName,
    [Required, MaxLength(64)] string Sku,
    [Range(0, long.MaxValue)] long UnitPrice,
    [Range(1, 10)] int Quantity = 1);

Do module Cart không được reference trực tiếp CatalogDbContext (nguyên tắc kiến trúc), hiện chưa có nguồn giá server-side. Nếu implement task 19 theo đúng contract này, client có thể gửi UnitPrice = 1 và mua iPhone với giá 1 đồng.

Cách sửa đề xuất: đổi AddToCartRequest thành chỉ nhận ProductVariantId + Quantity. Giá, tên, SKU phải tra từ Catalog qua contract/event bus (task N2LHTBLTT-29 của Mạnh). Trong lúc chờ contract, endpoint nên trả lỗi 501/503 thay vì đọc giá từ client. Cần chốt với Mạnh trước khi làm task 19.
F-02 · High Chưa có logic sinh OrderNumber trong domain

Order.Create() nhận orderNumber từ bên ngoài dưới dạng tham số, không tự sinh. Repository có ExistsOrderNumberAsync để kiểm tra trùng, nhưng chưa có nơi sinh số. Định dạng đã thống nhất trong test là ORD-20261025-0001 — cần một generator an toàn khi chạy song song.

Cách sửa đề xuất: sinh mã ở tầng service (task 20) theo dạng ORD-{yyyyMMdd}-{seq:D4}, dùng sequence PostgreSQL hoặc retry khi đụng unique constraint. Không nên để client quyết định.
F-03 · High Ma trận chuyển trạng thái chưa được kiểm soát chặt

ChangeStatus() chỉ chặn chuyển từ DELIVERED hoặc CANCELLED. Điều này cho phép các bước nhảy không hợp lệ, ví dụ PENDING → DELIVERED hoặc PENDING → SHIPPING mà không qua CONFIRMED.

if (Status == OrderStatus.DELIVERED || Status == OrderStatus.CANCELLED)
{
    throw new InvalidOperationException($"Không thể chuyển trạng thái từ {Status} sang {newStatus}.");
}
Cách sửa đề xuất: thêm bảng transition hợp lệ, ví dụ AllowedTransitions = { PENDING: [CONFIRMED, CANCELLED], CONFIRMED: [SHIPPING, CANCELLED], SHIPPING: [DELIVERED, DELIVERY_FAILED], … }. Đây cũng là nơi để luật "hủy đơn phải trả lại tồn kho" (task 26) gắn vào.
F-04 · Medium Ngưỡng miễn phí ship đặt sơ bộ — cần xác nhận nghiệp vụ

FreeShippingThreshold = 10_000_000 (10 triệu) và StandardShippingFee = 30_000. Ban đầu tôi đặt ngưỡng 500.000 nhưng đó là con số vô lý trong bán điện thoại — một chiếc iPhone đã vượt ngưỡng, khiến quy tắc "miễn phí ship" trở nên vô nghĩa. Số 10 triệu là giá trị tạm để khớp với phụ kiện rẻ.

Cần bạn xác nhận: đây là chính sách ship thật của CellphoneS hay số tạm? Nếu ship luôn miễn phí (phổ biến ở e-commerce điện thoại) thì nên bỏ hẳn ShippingFee khỏi entity.
F-05 · Medium PaymentMethod là string thay vì enum

Trong khi Status dùng enum và được lưu dạng string, PaymentMethod lại là string gán cứng "COD". Không nhất quán, và không có chỗ mở rộng khi thêm chuyển khoản / ví điện tử ở sprint sau.

Cách sửa đề xuất: tạo enum PaymentMethod { COD, BANK_TRANSFER, MOMO, VNPAY }, lưu dạng string. Nhất quán với cách xử lý OrderStatus.
F-06 · Low RecalculateTotals() là public — để lộ mutation

Phương thức này tái tính Subtotal/ShippingFee/TotalAmount từ danh sách item. Hiện chỉ được gọi nội bộ trong Create(), nhưng để public nghĩa là bất kỳ tầng nào cũng có thể gọi nó và thay đổi tổng tiền của đơn sau khi đã tạo.

Cách sửa đề xuất: đổi thành private và chỉ cho phép gọi qua các method nghiệp vụ được kiểm soát.

5.5 Quy tắc hủy đơn — đã hiện thực

public void Cancel(string reason)
{
    if (Status != OrderStatus.PENDING && Status != OrderStatus.CONFIRMED)
    {
        throw new InvalidOperationException($"Đơn hàng đang ở trạng thái {Status} không thể hủy.");
    }

    var previousStatus = Status;
    Status = OrderStatus.CANCELLED;
    CancelReason = reason.Trim();
    CancelledAt = DateTimeOffset.UtcNow;
    _statusHistories.Add(OrderStatusHistory.Create(this, previousStatus, OrderStatus.CANCELLED, CancelReason));
    Touch();
}
Phần còn thiếu: hủy đơn phải hoàn lại tồn kho. Hiện domain chỉ đổi trạng thái — chưa phát DomainEvent để module Inventory nhận và trả kho. Sẽ xử lý ở task N2LHTBLTT-26 cùng cơ chế event bus của Mạnh.

Cần bàn với Mạnh: dùng TransactionScope (hỗ trợ giao dịch phân tán trên cùng connection) hay chuyển sang ExecutionStrategy + shared transaction. Đây là quyết định kiến trúc, không nên tự quyết.

7. Cấu hình EF Core mapping

7.1 Bảng cart.carts & cart.cart_items

modelBuilder.Entity<CartEntity>(entity =>
{
    entity.ToTable("carts");
    entity.HasKey(e => e.Id);
    entity.Property(e => e.Id).UseIdentityAlwaysColumn();
    entity.Property(e => e.Status).HasConversion<string>().HasMaxLength(20).IsRequired();
    entity.Property(e => e.CreatedAt).HasDefaultValueSql("now()").IsRequired();
    entity.Property(e => e.UpdatedAt).HasDefaultValueSql("now()").IsRequired();

    entity.HasIndex(e => e.UserId);
    entity.HasIndex(e => new { e.UserId, e.Status });   // hỗ trợ truy vấn giỏ active

    entity.HasMany(e => e.Items)
        .WithOne()
        .HasForeignKey(item => item.CartId)
        .OnDelete(DeleteBehavior.Cascade);
});

7.2 Bảng ordering.orders

entity.Property(e => e.OrderNumber).HasMaxLength(32).IsRequired();
entity.Property(e => e.Status).HasConversion<string>().HasMaxLength(20).IsRequired();
entity.Property(e => e.PaymentMethod).HasMaxLength(20).IsRequired();
entity.Property(e => e.ReceiverPhone).HasMaxLength(20).IsRequired();
entity.Property(e => e.ShippingAddress).HasMaxLength(500).IsRequired();
entity.Property(e => e.Note).HasMaxLength(500);
entity.Property(e => e.CancelReason).HasMaxLength(500);

entity.HasIndex(e => e.OrderNumber).IsUnique();
entity.HasIndex(e => e.CustomerId);
entity.HasIndex(e => new { e.Status, e.CreatedAt });   // lọc đơn theo trạng thái + ngày

✔ Điểm tốt

  • Enum lưu dạng string → đọc log DB dễ hiểu, không phụ thuộc thứ tự giá trị.
  • Đặt tên bảng snake_case đúng convention PostgreSQL.
  • UseIdentityAlwaysColumn() nhất quán với Catalog/Identity.
  • HasDefaultValueSql("now()") cho cả CreatedAt/UpdatedAt.
  • Index phù hợp với truy vấn thực tế (giỏ theo user, đơn theo trạng thái + ngày).
  • Unique index (CartId, ProductVariantId) chống trùng item trong cùng giỏ.
  • Cascade cho Items/Histories — xoá đơn thì dọn luôn bản ghi con.

⚠ Cần chú ý

  • PaymentMethod cần đổi thành enum nếu chọn F-05.
  • UpdatedAt không có trigger tự cập nhật — phải gọi Touch() thủ công (domain đã làm).
  • Chưa có migration — thuộc task N2LHTBLTT-13 của Đạt.
  • Index (CartId, ProductVariantId) unique: nếu nghiệp vụ cho phép cùng variant ở 2 dòng (khác màu, khác dung lượng) thì sai — hiện chỉ khóa theo ProductVariantId nên vẫn đúng.
F-09 · Info Xung đột namespace C# giữa tên module và tên entity

Module tên Cart và Order trùng với tên entity Cart và Order, gây lỗi CS0118: 'Order' is a namespace but is used like a type ở mọi file ngoài thư mục Domain/Entities. Đã xử lý bằng alias:

using OrderEntity = PhoneStore.Modules.Order.Domain.Entities.Order;
using CartEntity  = PhoneStore.Modules.Cart.Domain.Entities.Cart;
Cần lưu ý: module Inventory (của Đạt) nhiều khả năng cũng có entity trùng tên — nên thống nhất quy ước alias này trước khi các bạn code. Đề xuất ghi vào GIT_WORKFLOW.md.

F-10 · Low Magic number lặp lại giữa DTO và Domain

[Range(1, 10)] trong AddToCartRequest và UpdateCartItemRequest trùng với CartItem.MaxQuantityPerItem = 10. Nếu đổi giới hạn ở domain mà quên sửa DTO, validation ở tầng HTTP sẽ khác với tầng domain.

Cách sửa đề xuất: dùng hằng số trong attribute không được (phải là const compile-time) — nên chấp nhận lặp lại và ghi chú, hoặc bỏ [Range] ở DTO và để domain là nguồn sự thật duy nhất rồi bắt exception ở tầng global (task 14).

11. Checklist review

Dùng làm danh sách kiểm tra khi review pull request.

Kiến trúc & convention

  • Entity dùng private set + static Create() factory — đúng convention Catalog/Identity
  • Quy tắc nghiệp vụ nằm trong domain, không lọt sang service
  • Mỗi module giữ DbContext riêng, schema riêng, migration history riêng
  • Không module nào reference trực tiếp DbContext của module khác
  • Architecture test kiểm tra ranh giới cho cả Cart và Order
  • Enum lưu dạng string trong DB (đọc log dễ, không phụ thuộc thứ tự)
  • Index phù hợp truy vấn thực tế

Nghiệp vụ Cart

  • Thêm cùng variant → cộng dồn thay vì tạo dòng trùng
  • Giới hạn 50 dòng khác nhau / giỏ
  • Giới hạn 10 đơn vị / dòng
  • Giỏ đã CONVERTED không thêm/sửa/xoá được
  • Chặn thao tác lên item không thuộc giỏ
  • Chặn thêm sản phẩm đã ngừng bán / hết tồn (cần contract từ Catalog)
  • Giỏ có hạn dùng — tự chuyển ABANDONED sau N ngày không cập nhật

Nghiệp vụ Order

  • Đơn mới luôn PENDING, thanh toán COD
  • Lịch sử trạng thái ghi lại mọi lần chuyển
  • Chỉ hủy được khi PENDING / CONFIRMED
  • Từ DELIVERED / CANCELLED không chuyển trạng thái được nữa
  • Set DeliveredAt khi giao thành công
  • Set CancelledAt + CancelReason khi hủy
  • Mã đơn sinh tự động, duy nhất, không đoán được
  • Ma trận chuyển trạng thái được ràng buộc đầy đủ
  • Tính lại giá từ Catalog tại thời điểm checkout, không tin giá trong giỏ
  • Hủy đơn → hoàn tồn kho qua event
  • Chống race khi 2 request cùng checkout 1 giỏ (khóa / idempotency)
