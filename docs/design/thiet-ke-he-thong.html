1 Kiến trúc tổng thể

Hệ thống chọn Modular Monolith kết hợp Clean Architecture. Mỗi nghiệp vụ là một module độc lập với vòng đời, schema CSDL và contract riêng; các module chia sẻ một Shared Kernel ở tầng BuildingBlocks.

2 Ranh giới module & quy tắc phụ thuộc

Mỗi module là một "hồ" độc lập: có schema riêng, DbContext riêng, contract riêng. Đây là ranh giới được kiểm chứng tự động bằng 7 architecture test, không phải chỉ quy ước trên giấy.

Quy tắc BR-20 — Không rò rỉ tham chiếu: module không được using namespace Infrastructure hay DbContext của module khác. Thay vào đó:
  • Cần đọc dữ liệu → phụ thuộc vào Contract (interface do BuildingBlocks định nghĩa)
  • Cần thông báo thay đổi → phụ thuộc vào Domain Event + Event Bus
  • Không có trường hợp nào cần biết DbContext của module khác

2.1. Vì sao chọn Modular Monolith thay vì Microservice

Phù hợp với đồ án

  • Quy mô nhóm 5 người — microservice sẽ tốn quá nhiều thời gian vận hành
  • Chưa có yêu cầu scale độc lập theo từng nghiệp vụ
  • Cần giao dịch xuyên module (checkout ghi cả `ordering` và `cart`) — trong monolith dùng TransactionScope là gọn, trong microservice phải chấp nhận eventual consistency
  • Triển khai 1 lần, quan sát 1 chỗ — phù hợp môi trường đồ án

Đường mở rộng sau này

  • Contract đã là điểm gắn sẵn — thay HTTP call thay vì in-process là thay implementation, không phải thiết kế lại
  • Inventory tách ra service riêng là ứng viên đầu tiên (tồn kho cần scale độc lập)
  • Event Bus đã dùng MediatR — có thể thay bằng RabbitMQ/Kafka mà không đổi code nghiệp vụ
  • Database đã tách schema — có thể tách instance dần

3.2. Quy ước thiết kế CSDL

Định danh

  • PK: BIGINT — UseIdentityAlwaysColumn() (identity always, không dùng serial)
  • Tiền tệ: BIGINT — lưu số nguyên VND, không dùng float/double
  • Số lượng: INTEGER
  • Thời gian: TIMESTAMPTZ — luôn UTC
  • Enum: lưu dạng TEXT qua HasConversion<string>()

Ràng buộc

  • Unique index cho dữ liệu định danh nghiệp vụ: Email, Sku, OrderNumber, Brand.Name
  • FK bắt buộc cho quan hệ sở hữu: Cart→CartItem, Order→OrderItem/History
  • DeleteBehavior.Cascade cho quan hệ sở hữu
  • Index phục vụ truy vấn: CustomerId, Status+CreatedAt, ProductVariantId

Đặc biệt của Order

  • Snapshot: order_items lưu ProductName, Sku, UnitPrice tại thời điểm mua — không join sang catalog khi xuất hóa đơn
  • Thêm giá mới không làm đơn cũ thay đổi giá trị
  • Đơn vị vị trí dữ liệu: ProductVariantId chỉ là tham chiếu logic, không FK chéo schema
Quyết định cần đánh giá lại khi tách module: order_items.ProductVariantId và cart_items.ProductVariantId hiện là tham chiếu logic (không có FK vật lý) tới bảng catalog.product_variants — đây là chủ ý để giữ ranh giới schema. Đổi lại: không thể dùng FK cascade giữa các schema, và cần kiểm soát orphan record bằng logic ứng dụng.

    public TId Id { get; protected set; }
    public DateTimeOffset CreatedAt { get; protected set; }
    public DateTimeOffset UpdatedAt { get; protected set; }
    public void Touch() => UpdatedAt = DateTimeOffset.UtcNow;
}

Áp dụng cho: CartItem, OrderItem, OrderStatusHistory, Address, ProductVariant, ProductImage, ProductStock

AggregateRoot — thêm cơ chế event

public abstract class AggregateRoot<TId> : BaseEntity<TId>
{
    private readonly List<IDomainEvent> _domainEvents = [];
    public IReadOnlyCollection<IDomainEvent> DomainEvents
        => _domainEvents.AsReadOnly();

    public void AddDomainEvent(IDomainEvent e) => _domainEvents.Add(e);
    public void ClearDomainEvents() => _domainEvents.Clear();
}

Áp dụng cho: User, Product, Cart, Order — chỉ aggregate root được phát domain event
